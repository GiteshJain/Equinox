Decision #9. GitHub runs these on every pull request and every change to `main` (`.github/workflows/checks.yml`). The
result, with anything that failed, is posted as a comment on the pull request. While any check is red, nothing is merged.

Run them all: `bash tests/run_all.sh` (needs Python with Playwright 1.56 and its Chromium, and Node 22). The new
planner's and the planning library's own steps alone: `npm ci`, then `npm run typecheck`, `npm run lint`, `npm test`,
`npm run build`; then `python3 tests/rules_planpy_test.py` for the optimiser against plan.py.

**The new planner's types.** `app/planner/src/db/types.ts` is generated, never edited by hand: the rehearsal makes it
from last night's copy after the pull request's migrations. A pull request that changes the database's tables, views or
functions in `public` updates it in the same pull request: push, let the rehearsal fail on the types, download its
`planner-types` artifact (`gh api repos/<owner>/<repo>/actions/runs/<run id>/artifacts`, then the artifact's
`archive_download_url`), commit the `types.ts` in it, and push again.

## Database tests
Each file in `database/tests/` runs on the rehearsal's copy, after the new migrations, in a transaction that is rolled
back. A failed check stops with an error that says which. A passing test's notices (counts, never rows) are printed
under its `ok`.

**Before and after.** The files in `database/tests/before/` run before the new migrations and save chosen outputs into
the schema `rehearsal_before` (the data API, the row counts and the table guide don't look at it), so a test can
compare them afterwards. `capture_outputs.sql` saves the three capture views, `export_capture()` (every captured row)
and `planner_loads`; `planner_load_before.sql` how many of the capture's flights had both their money and their loads;
`website_scripts_before.sql` `site_public()`, `site_investor()` and `site_report()` (with a throwaway investor
password, removed again), `export_for_report('planner')`, `export_planner_data()` and when `planner_state` was last
saved; `switch_over_before.sql` whether the old rows were already frozen in the backup, so a test can tell the night of
the switch-over (frozen during the rehearsal, still equal to the getters) from the nights after (older than the tables
by design); `history_before.sql` `export_for_report()`'s scan kinds (the list of scans, every scan's airlines and
airports), `export_planner_data()` and `export_repo_bootstrap()`, each balance-sheet and income-statement row's capture
time, and whether the daily history was there already (so the backfill is checked exactly on the night it runs);
`jobs_before.sql` every backup run as `backup_runs` reads (every column but `id`), and whether the copy had the jobs
already. After the new migrations the rehearsal pauses any job they schedule on the copy (`pg_cron`), so none runs during
the tests or the real saves, and keeps their state as the migrations left it in `rehearsal_before.cron_jobs`.

## Real saves (#17)
The rehearsal starts Supabase's database, data API and sign-in, and nothing else, then restores the backup. The test
makes two throwaway users through the local sign-in (one in `planner_users`, one not). The planner's requests for the
live Supabase address are answered by the local copy, with the local key in place of the live one; its Supabase
library is the version it names, from npm. Every other outside request is stopped, and the test fails if anything
reached the network except the local server.
- **Plan card title:** the planner has no field for it, so the test uses Reference → Data: export, change the title,
  import. That saves the whole document, which also proves an export and import change nothing else.
- **Typed load:** typing a day under Loads by hand replaces that day's whole entry with what's in the boxes (only
  flights under 95%). So the test types on the latest recent day with no loads yet, where nothing else can change.
- **The items** (the first open to-do, the first plan card, the day and flight) are picked from the restored data each
  run. `savedAt` and `version` may change with any save; a missing field counts the same as an empty (null) one.
- **Two tabs:** two browsers sign in and load the same version. The first ticks a to-do on Home; the second, through
  its backup screen, saves new titles for that to-do (a clash) and another (no clash), then, after its reload, that
  to-do's title again.
- **A copy kept offline:** the test cuts one browser's requests to the database, as if the network were down. That
  browser saves new titles for two to-dos through its backup screen, so the cloud save fails and the planner keeps a
  copy with the version it had loaded. A second browser ticks the first to-do. The first browser's tab closes and
  opens again online, and pushes the copy from that stored version.
- **A preview** is the planner at `127.0.0.1` (any address but the live one, #8): it signs in, reads, and a tick saves
  nothing; the test counts which functions reached the copy.
- **The rollback** runs last, since it changes the copy for good: `private.unfreeze_planner_state()`, then the old
  planner (commit `eb4c3ef`, the last that saved `planner_state` itself, read with `git show` and served the same way)
  signs in and ticks a to-do.
- The log is posted on the pull request, so it shows ids and the names of changed fields only, never rows or keys.

To try it on your machine (Docker, the Supabase CLI, psql 17, Python with Playwright, Node): get a backup as below,
then `bash database/rehearse.sh .backup`.

## The sample
`fixtures/sample_<date>.json.gz` is what the planner and website read at one moment (`frozen_at`), taken from a nightly
backup by `fixtures/make_sample.sh` (the reads are `fixtures/sample.sql`). The tests freeze the clock at that moment, so
the answers don't drift. The checks use the newest sample; `sample_2026-10-08.json.gz` stays for
`planner_load_sample_test.sql`, which loads it the old way.
Since the switch-over (#13, pull request 9) the sample is made the new way: the backup first gets every change in
`database/migrations/` it doesn't have yet, then the planner's document and loads are what `planner_state_get()` and
`planner_loads_get()` give, as the planner now reads them. It also carries `settings`, `world_rules` and
`planner_meta`'s growth rules, for the rule numbers check. The checks' stand-in for the database (`harness.py`) answers
the adapter's calls from it.
`fixtures/game_schedule_113.html.gz` is Kingfisher's public schedule page from the game, saved signed out.

These are the one exception to "no game data in the code repository" (decision #9). They are small and dated, and
never hold the database, keys or sign-in data.

**Getting a backup to make a sample from.** The nightly copies are in the Cloudflare R2 bucket `equinox-backups`
(decision #16). You need the AWS CLI, jq and the R2 reader key (read-only). From the repository root:

```bash
export R2_ENDPOINT="https://<account id>.r2.cloudflarestorage.com"
export AWS_ACCESS_KEY_ID="<reader key id>" AWS_SECRET_ACCESS_KEY="<reader secret>"
bash database/backup/download.sh .backup   # latest.json, then the copy it names: checks the SHA-256 and unpacks it
bash tests/fixtures/make_sample.sh .backup 2026-10-08T21:00:00Z
rm -rf .backup                             # git ignores .backup/, but don't keep live data around
```

For an older night, download `nightly/equinox-backup-<date>T<time>Z.tar.gz` (kept 30 days) or
`monthly/<YYYY-MM>.tar.gz` (kept for good) together with its `.sha256`, into one folder and with the same names. Check
it with `sha256sum -c <file>.sha256`, then unpack it with `tar -xzf <file> -C <new folder>`.

**Without the R2 key.** A pull request that changes `fixtures/make_sample.sh` or `fixtures/sample.sql` gets a new sample
from the database rehearsal's own copy, after its changes and before any test touches it, as of the backup's time. It
is the run's `test-sample` artifact, kept one day: download it (`gh api repos/<owner>/<repo>/actions/artifacts`), run
`python3 tests/check_secrets.py` over it, and commit it with the answers it moves.

## When an answer changes
- **Unintended:** the check caught a bug, so fix it.
- **Intended** (a calculation was meant to change): run `python3 tests/planner_test.py --update`, or
  `node tests/schedule_test.mjs --update` for the schedule check. Commit the new `*.expected.json` with the change, and
  say in the pull request which answers moved and why.
- **A new bug fixed:** add a test that would have caught it.
- **The data model changes** (#13): make a new sample with `make_sample.sh` and update the answers in the same pull
  request.
