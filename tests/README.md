result, with anything that failed, is posted as a comment on the pull request. While any check is red, nothing is merged.

## Database tests
Each file in `database/tests/` runs on the rehearsal's copy, after the new migrations, in a transaction that is rolled
back. A failed check stops with an error that says which. A passing test's notices (counts, never rows) are printed
under its `ok`.

**Before and after.** The files in `database/tests/before/` run before the new migrations and save chosen outputs into
the schema `rehearsal_before` (the data API, the row counts and the table guide don't look at it), so a test can
compare them afterwards. `capture_outputs.sql` saves the three capture views and `export_capture()` (every captured
row); `website_scripts_before.sql` `site_public()`, `site_investor()` and `site_report()` (with a throwaway investor
password, removed again); `history_before.sql` `export_for_report()`'s scan kinds (the list of scans, every scan's
airlines and airports) and `export_repo_bootstrap()`, each balance-sheet and income-statement row's capture time, and
whether the daily history was there already (so the backfill is checked exactly on the night it runs); `jobs_before.sql`
every backup run as `backup_runs` reads (every column but `id`), and whether the copy had the jobs already;
`rules_input_before.sql` `rules_input()`'s document, so the test can show `'all'` is unchanged; `clean_up_before.sql`
each aircraft's places in the old lists, the captured figures at one moment, the old planner's loads days and each
archived table's manifest for last month (the clean-up's test). After the new migrations the rehearsal pauses any job
they schedule on the copy (`pg_cron`), so none runs during the tests or the saves, and keeps their state as the
migrations left it in `rehearsal_before.cron_jobs`.

## The planner on the copy (#17, #18)
The rehearsal starts Supabase's database, data API and sign-in, and nothing else, then restores the backup. The tests
make throwaway users through the local sign-in (one in `planner_users`, one not). The planner's requests for the live
Supabase address are answered by the local copy, with the local key in place of the live one. Every other outside
request is stopped, and a test fails if anything reached the network except the local server. The log is posted on the
pull request, so it shows table, column and screen names, ids and counts only, never rows or keys. (Until the clean-up,
`real_saves_test.py` did this for the old planner, and the side by sides compared each screen with it.)

To try it on your machine (Docker, the Supabase CLI, psql 17, Python with Playwright, Node): get a backup as below,
then `bash database/rehearse.sh .backup`.

## The sample
`fixtures/sample_<date>.json.gz` is what the website reads at one moment (`frozen_at`): `site_public()`'s feed, taken
from a nightly backup by `fixtures/make_sample.sh` (the read is `fixtures/sample.sql`; the backup first gets every change
in `database/migrations/` it doesn't have yet). The website check freezes the clock at that moment, so the answers don't
drift, and uses the newest sample. Samples made before the clean-up also carry the old planner's document and loads, the
route research and the tables its capture board read, for the old planner's checks, which went with it;
`report_test.py` leaves the 10 Oct sample's old document beside the weekly report, which must not read it.
`fixtures/game_schedule_113.html.gz` is Kingfisher's public schedule page from the game, saved signed out.
`fixtures/optimiser_kul_2026-10-10.json` is the planning library's optimiser case made from `sample_2026-10-10`: the 60
legs arriving at or leaving KUL, as `rules_input()` gives them, three destinations to plan and `plan.py`'s answer, saved
before plan.py was retired (#19). The library's Vitest cases and `optimiser_saved_answer_test.py` both run it.

**The report sample.** `fixtures/report_<date>.json.gz` is what the weekly report's scripts read, at one moment (the
backup's), as `export_for_report()` gave it on the rehearsal's copy: the captured figures (kind `figures`), the planning
library's input (kind `rules`) and the latest finished world scan, plus the website's airlines (`site_public()`), made by
`fixtures/report_sample.sql` and cut to what the report needs by `fixtures/report_sample.py` (which says what it keeps:
every airline's cash forecast without its payments, 14 days of profit, the best and worst routes over 7 days, the cards,
hubs first and the growth lists; our airlines' legs, aircraft and bases with only the routes and airports they use; our
airlines' and 12 rivals' schedules and our bases' airport pages). A pull request that changes either file gets a new one
as the rehearsal's `report-sample` artifact: download it, run `python3 tests/check_secrets.py` over it, commit it, and
cut `fixtures/report_airports_oa.csv` again from OurAirports' `airports.csv` (ourairports.com/data, public) to the
airports it uses. `report_test.py` runs the newest one.

These are the one exception to "no game data in the code repository" (decision #9). They are small and dated, and
never hold the database, keys or sign-in data.

**Getting a backup to make a sample from.** The nightly copies are in the Cloudflare R2 bucket `equinox-backups`
(decision #16). You need the AWS CLI, jq and the R2 reader key (read-only). From the repository root:

```bash
export R2_ENDPOINT="https://<account id>.r2.cloudflarestorage.com"
export AWS_ACCESS_KEY_ID="<reader key id>" AWS_SECRET_ACCESS_KEY="<reader secret>"
bash database/backup/download.sh .backup   # latest.json, then the copy it names: checks the SHA-256 and unpacks it
bash tests/fixtures/make_sample.sh .backup 2026-10-08T21:00:00Z
rm -rf .backup                             # git ignores .backup/, but don't keep live data around
```

For an older night, download `nightly/equinox-backup-<date>T<time>Z.tar.gz` (kept 30 days) or
`monthly/<YYYY-MM>.tar.gz` (kept for good) together with its `.sha256`, into one folder and with the same names. Check
it with `sha256sum -c <file>.sha256`, then unpack it with `tar -xzf <file> -C <new folder>`.

**Without the R2 key.** A pull request that changes `fixtures/make_sample.sh` or `fixtures/sample.sql` gets a new sample
from the database rehearsal's own copy, after its changes and before any test touches it, as of the backup's time. It
is the run's `test-sample` artifact, kept one day: download it (`gh api repos/<owner>/<repo>/actions/artifacts`), run
`python3 tests/check_secrets.py` over it, and commit it with the answers it moves.

## When an answer changes
- **Unintended:** the check caught a bug, so fix it.
- **Intended** (a calculation was meant to change): run `UPDATE_FIGURES=1 node tests/planner_figures.mjs` for the
  screens' figures, or `node tests/schedule_test.mjs --update` for the schedule check. Commit the new `*.expected.json`
  with the change, and say in the pull request which answers moved and why.
- **A save meant to write other rows:** the rehearsal's `planner-saves` artifact holds every save's answer as the run
  found it (`planner_saves.json`); commit it as `fixtures/planner_saves.expected.json` with the change, and say in the
  pull request which saves changed and why.
- **A new bug fixed:** add a test that would have caught it.
