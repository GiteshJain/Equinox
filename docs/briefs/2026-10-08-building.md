## How Claude Code works
- **What it is.** Claude Code is Claude working directly on code. A cloud session runs on a computer in Anthropic's
  cloud. It clones a GitHub repository, edits files, runs commands and tests, pushes a branch and opens a pull request.
  You start one at claude.ai/code or in the Code tab of the Claude app: pick the repository and describe the task. It
  keeps working with the phone put away.
- **This chat already uses the same machinery.** Behind the scenes it runs on the same kind of cloud computer. That is
  how it cloned the repository, ran the checks and opened pull requests #1 to #8. Switching adds no new abilities. It
  changes how the work is split and what each session remembers.
- **What a separate session starts with:**
  - a fresh clone of the repository and its `CLAUDE.md` (none exists yet);
  - the skills and connectors on the account, so the Supabase connector would work.

  It does not get this project's files, its memory, past chats or the discussion behind a decision.
- **Extras:**
  - a diff view with line comments;
  - auto-fix: it watches a pull request and fixes failing checks or review comments (needs the Claude GitHub App on the
    repository);
  - several sessions at once;
  - routines (scheduled runs), relevant at #22.
- **Setup for B:**
  - connect GitHub (the Claude GitHub App);
  - a cloud environment. The default reaches package registries and GitHub only; direct calls to Supabase need its
    address added (the connector works without it). Its environment variables are readable by anyone using it.
- **Cost.** Cloud sessions share the plan's limits with chats, with no separate charge for the cloud computer.
  Parallel sessions use the limits faster.
- **Projects (D).** A public beta on Pro and Max. It reaches accounts that don't have chat projects first, and there's
  a waitlist.

## What the problem actually is
- The old Building chat ran out of space once on 8 Oct and was summarised, and details were lost.
- The rebuild (#13 to #25) is much bigger than #1 to #12: the data model, the planner rebuilt screen by screen, the
  shared library, jobs and monitoring.
- The planner is one 578 KB file (3,449 lines). Every build that touches it reads parts of it. In one chat, those reads
  pile up.
- What fixes it is a clean memory for each build. B, C and D all give that; A doesn't.

## Why C over B
- **The same fix, without the extra steps.** Under B, every pull request means going to the Code tab, pasting a brief
  and coming back here. Over the rebuild's many pull requests, that friction adds up, and the work sits in two places.
- **This chat keeps what the builds need:** the decisions as they're made, the project files, memory, the Supabase
  connection and the reason behind each rule. Each helper gets a written spec from this chat with exactly what it needs.
- **The safeguards don't change:**
  - every pull request still runs *Checks* and the database rehearsal;
  - a red check blocks the merge;
  - Gitesh says "merge".
- **What B has that C doesn't:** watching and steering a build live, line comments on the diff, and auto-fix. Under
  the one-item-at-a-time rule Gitesh reviews results, not steps, and red checks are fixed before Claude asks for
  "merge" anyway.

## How C would run
1. Decide here, with a brief where it's a decision.
2. Claude writes the build spec: what, why, which files, and what the checks should show. A helper with a fresh memory
   gets the spec, reads the map and the manual, writes the code, runs the checks and opens the pull request.
3. Claude reviews the pull request against the spec and the checks, fixes it or sends it back, and only then asks for
   "merge".
4. A new Building chat at the start of each step (Step 4, Step 5). Anything worth carrying goes into the repository or
   the project files first.
5. A short `CLAUDE.md` in the repository, pointing to the map and the manual, so helpers, any later Claude Code session
   and #22's scheduled jobs all start from the same place.

## Scenarios and the risk of waiting
- **C works:** builds land cleanly and this chat stays readable. Revisit only if Projects reaches the account.
- **C struggles** (a helper misreads specs repeatedly, or reviews drag): switch to B. About 15 minutes of setup;
  nothing is lost, since everything is in GitHub.
- **Waiting** costs nothing until #13 starts. #13 is the first big build, so this should be settled before it.
- **The trial:** under C, the first #13 build is the trial, reviewed afterwards. Under B, a small documentation fix
  first: three lines still say #11 replaces the ingest secret, which #11 kept.

## What would change the recommendation
- Gitesh wants to watch and steer builds as they happen: B.
- Projects appears in the Code tab: D, which is C with a dashboard and its own memory.
- The first #13 build under C goes badly: B.
- Running several builds at once becomes useful (it isn't, under one item at a time): B or D.
