# Automatic tests — 8 Oct 2026 (decision #9)

**Decision:** which tests run by themselves on every change, and what stops a change that fails them.
**Recommendation:** B. A set of automatic checks runs on every pull request: every planner screen opens, key numbers
match known answers, the website works, there are no keys in the code, and the database rehearsal from #8 runs. A
failing check blocks the merge by rule. It costs $0 and about half a day to build, and stays small because the planner
is rebuilt at #18.

*Columns adapted for a non-game decision: protection instead of growth, real money instead of game profit.*

| Option | Protection | Cost | Opportunity cost | Risk | Easy to undo? |
|---|---|---|---|---|---|
| A. As now | Claude runs 2 tests by hand before a pull request | $0 | None | A broken screen or wrong number can reach live; nothing stops a merge | — |
| **B. Automatic checks, blocking by rule** | **5 checks on every pull request, results on the pull request; red means no merge** | **$0 (GitHub's free minutes)** | **About half a day to build; tests for code that #18 rewrites** | **The block is a rule Claude follows, not a lock** | **Yes** |

B + a lock on `main` | As B, and GitHub itself refuses a change that hasn't passed | $0 with the Student Developer Pack (GitHub Pro); otherwise paid | As B, and every rule and doc change from every chat must go through a pull request too | Slower rule updates; an apply step for the Student Pack | Yes |

## Background
- **Tests today:** there are 11 test files in `tests/` and none runs by itself.
  - Two run from the repository: the cash-forecast test and the ordering-screen test, written on 8 Oct.
  - The other nine were recovered from the old workspace and depend on files lost in the reset: a test harness and
    exported live data. They covered route profit, the fare plan, the Review checks, filing, the save safeguard and
    the salary step.
- **Automatic checks today:** Cloudflare's build of each pull request, and since #8 the database rehearsal, which runs
  only on pull requests that change the database.
- **What B would check, on every pull request:**
  1. **Every planner screen opens** with a saved day of data and no errors: Home, Routes, Tails, Hubs, Check, Review,
     Interline, Photos, Reference and the main pop-ups.
  2. **Key numbers match known answers** on that saved day: cash forecast and leases, route profit, fare plan, the
     Review cards. These are rebuilt from the recovered tests on one shared setup.
  3. **The website works:** every public page opens, and the schedule check reads a saved game page correctly.
  4. **No keys or passwords in the code.** This enforces the standing rule.
  5. **The database rehearsal** (#8), when the database changes.

  From then on, every bug fixed gets a test that would have caught it. The results are posted on the pull request.
  Claude never asks for, or makes, a merge while a check is red, and this is written into the manual.
- **Test data:** B uses small frozen samples, such as one day's capture and one saved game page, kept in
  `tests/fixtures/`. The README says live game data is never committed. The 6 KB forecast sample from 8 Oct is
  already there, so B needs a stated exception: small dated samples for tests only, never the database, keys or
  sign-in data. The alternative is reading last night's backup at test time. That keeps data out of the repository,
  but the answers change every night, so exact-answer checks wouldn't work.
- **GitHub limits (GitHub's plans page):**
  - The free plan gives 2,000 Actions minutes a month for private repositories; Pro gives 3,000.
  - Protected branches, which would make GitHub refuse an unchecked change, are not available on private
    repositories on the free plan. Checking ours on 8 Oct, GitHub answered "Upgrade to GitHub Pro or make this
    repository public".
  - The Student Developer Pack includes "Free GitHub Pro while you are a student" (education.github.com/pack).
- **Minutes used:** the nightly backup takes about 3 minutes (about 90 a month), a rehearsal about 2, and B's checks
  about 3 to 4 per push. Even 50 pushes a month stays well under 2,000.
- **Why the lock in C costs flexibility:** GitHub's lock applies to every change to `main`, so the rule and doc updates
  other chats commit directly would have to become pull requests as well. Exempting Claude from the lock would defeat
  its purpose, since Claude is the one who merges.

## Scenarios and the risk of waiting
- **Next few weeks:** small fixes to the current planner. Under A, a change that breaks a screen nobody looked at goes
  live unnoticed until you open it. Under B, the check fails on the pull request first.
- **The rebuild (#13 to #20):** many large changes. B's checks are what show that the new planner still gives the same
  answers as the old one: the known-answer tests carry over and are run against the rebuilt screens.
- **Waiting:** every change before B relies on Claude remembering which tests to run by hand, and nine of the eleven
  tests can't run at all.

## What would change the recommendation
- **If you'd like GitHub itself to enforce the block,** and are happy for rule changes to go through pull requests:
  C, after applying for the Student Developer Pack.
- **If you'd rather keep all game data out of the repository:** B with tests reading last night's backup. The checks
  become "no errors on real data" instead of exact answers.

## Outcome
**8 Oct 2026: B decided**, with the test-sample exception. Small dated samples of game data are allowed in
`tests/fixtures/` (never the database, keys or sign-in data). The manual and README record the exception now; the
blocking rule goes into the manual when the checks are merged.
