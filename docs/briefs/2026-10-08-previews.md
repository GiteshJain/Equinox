# Preview before live — 8 Oct 2026 (decision #8)

**Decision:** how changes are tried before they go live: what a preview may do with the live data, and where database
changes are tried first.
**Recommendation:** B. Previews show the live data but can't save, and every database change is first rehearsed
automatically on a copy restored from last night's backup. It costs $0 and closes both gaps, with no second database to
keep in step.

## Background
- **Previews today (since #7):** Cloudflare builds every pull request at its own address. Every preview uses the same
  database as the live site, because the planner's Supabase address and public key are fixed in the page
  (`web/planner/index.html`).
- **The planner saves itself** 0.3 seconds after every change, and again when the page closes. Each save overwrites
  the single `planner_state` row. The photos and logos editor writes to Storage and the site tables. So on a preview,
  any click that changes something writes over the live planner. A preview with an unmerged change to how state is
  stored would write that change into live data.
- **Database changes today:** Claude writes a migration file in the pull request and applies it to live with
  Supabase's migration tool after review. That's 31 changes since 24 Sep. None is tried anywhere first.
- **What B would do:**
  - Saving is switched off on every address except `equinox-alliance.com` (and `www`): the planner, monthly loads,
    photos and logos. A banner says "Preview: changes aren't saved". Reading still works, so a preview shows real data.
  - For every pull request that adds a migration, a GitHub Action restores last night's backup into a full local
    Supabase on GitHub's runner, the same way the nightly restore check already does (decision #6). It then applies
    the new migrations and reports on the pull request: applied cleanly or not, and the row count of each table before
    and after.
  - After "merge", Claude applies the change to live as now.
  - The data exists only on the runner while the check runs. Nothing is committed and the logs show only counts, so
    the code repository still never holds live data.
- **The read-only key:** the two repositories are private and can't read each other on their own. You'd create a
  GitHub token that can only read `equinox-backups` and paste it straight into a secret on the Equinox repository, never
  in chat. Its expiry goes on the To-do board.
- **Supabase plans (Supabase docs and pricing page):**
  - Branching needs the Pro plan ($25 a month) and is billed at $0.01344 an hour per branch.
  - New branches start without production data.
  - The free plan allows 2 active projects and pauses a project after a week without activity.
  - The "Equinox Alliance" organisation has one project today.

## Scenarios and the risk of waiting
- **Next few weeks:** mostly small planner and capture fixes. Under A, the main danger is a preview saving over the
  live planner while you test it. Under B, a preview can't, and a bad migration fails on the copy instead of on live.
- **The rebuild (#13 onwards):** #13 moves the planner's data out of the single row into proper tables. That means
  large database changes and new saving code. B's rehearsal covers the database changes. Trying the new saving code end
  to end would need C (or D) by then.
- **Waiting:** costs nothing today, but every preview you sign into before B is a chance to save into live data. The
  only recovery is last night's backup, which loses that day's changes and takes 15–30 minutes by hand.

## What would change the recommendation
- **The rebuild needs saving tested on previews:** add C at #13 or #18, or take D if #17 moves Supabase to its paid plan.
- **You'd rather not create the read-only key:** B still works, but the rehearsal runs on an empty copy built from the
  31 migration files instead of last night's data. It catches broken changes but not ones that fail only on real rows,
  such as a new rule that existing data breaks.

## Outcome
**8 Oct 2026: B decided.** Previews become look-only, and every database change is rehearsed on a copy of last
night's backup before it reaches live. Gitesh creates the read-only key for the backups. The operating manual gets the
rule when the build is merged.
