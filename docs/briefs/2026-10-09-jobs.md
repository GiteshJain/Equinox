# Scheduled jobs and their monitoring, brought forward — 9 Oct 2026 (parts of #22 and #23)

**Decision:** what runs the automatic jobs that #15 and #16 need, with which key, and how a job that didn't run gets
noticed. The 9 Oct consistency check found these jobs ship with #13, while #22 (scheduled jobs) and #23 (monitoring)
sat in Step 5. The first monthly archive is due 1 Dec.
**Recommendation:** B, a split by where the work is.
- **Jobs that only touch the database** run inside it, on Supabase's built-in scheduler (`pg_cron`), with no key
  leaving the database: the nightly snapshot and the clean-ups.
- **The one job that touches R2,** the monthly archive, runs in the nightly backup job, which already has the keys.
  It deletes rows only through a guarded database function that refuses anything inside the kept month.
- **Every job writes one row per run to a `job_runs` table.** The planner warns on Home when any job is late or
  failed, as it already does for backups.

It costs $0. The rest of #22 (weekly world scan, report drafts) and #23 stay in Step 5.

## Background
**The jobs, and when they're needed:**

| Job | What it does | Needs | Due |
|---|---|---|---|
| Nightly snapshot (#15) | One row per airline per day: fleet, departures, seats, cash, loads, profit; per route per day too (#16) | The database only | From the #13 build |
| Clean-ups (#16) | Raw statement lines and raw pages past 14 days | The database only | From the #13 build. Today the capture already clears raw pages after each capture |
| Monthly archive (#16) | Detail more than one full month old: write to R2 and the monthly release, check it, then delete the rows | The database and R2 | First run 1 Dec |
| Nightly backup (#6) | As now | The database and R2 | Running |
| Weekly world scan, report drafts (#22) | | The game's sign-in, Claude | Step 5, not now |

**The scheduler inside the database:**
- `pg_cron` is available on the free plan but not switched on yet. Switching it on adds, so it can be done from here.
- It runs database functions on a timetable.
- It keeps its own record of runs, and up to 32 jobs can run at once.
- It needs no password or key, because it runs inside the database.

**The snapshot's timing:** the capture runs in the Chicago evening, crossing midnight UTC.
- The snapshot is taken as soon as the world's capture for the day is complete (#14: all of that world's airlines).
- A timed run at 10:00 UTC (05:00 in Chicago) is the fallback. It takes the snapshot anyway, marked incomplete.
- "A day" is defined in the #13 design.

**The archive's safety:** it runs as a step in the nightly backup job on the first night after the 1st of each month.
1. It exports each month that's now more than one full month old.
2. It uploads the file to R2 and attaches it to that month's GitHub release, the second copy outside Cloudflare.
3. It checks both copies.
4. It calls `archive_delete(month, table, row count, checksum)`. That database function refuses any month inside the
   kept window and any count or checksum that doesn't match, so a bug can't delete the wrong rows.

The backup job already holds the database password and the R2 writer key, so nothing new is stored anywhere.

**Noticing:**
- One `job_runs` table records every run of every job: which job, when, whether it worked, a short note and, for
  copies, where the file went. It takes over from `backup_runs`, which stays readable under its old name.
- The planner's Home warns when:
  - a backup is more than 30 hours old;
  - a snapshot is more than 30 hours old;
  - an archive hasn't run by the 3rd of the month;
  - any job's last run failed.
- This is the part of #23 that's needed now. The rest of #23 (one place for captures, deploys and jobs) stays in
  Step 5.

**Keys (#11):** no automation account is added. The scheduler needs none. The archive reuses the backup job's
existing secrets, held only in `equinox-backups`. The guarded delete function, not a separate account, is what keeps
the one destructive job safe.

## Scenarios and the risk of waiting
- **GitHub starts the backup job hours late** on archive night: the archive is late too, which is harmless. The
  planner warns only if it hasn't run by the 3rd.
- **The capture is missed one evening:** the 10:00 UTC run takes the snapshot anyway, marked incomplete, so the trend
  has no hole.
- **The database's scheduler stops** (Supabase's guide mentions this can happen): the snapshot warning shows on Home
  within 30 hours. The fix is a restart from Supabase's settings.
- **Waiting:** the snapshot must start the day the #13 tables go live, or those days are missing for good. The archive
  must exist before 1 Dec.

## What would change the recommendation
- **If Supabase's scheduler proves unreliable:** move the snapshot to the backup job (option A for that job only).
- **When the weekly scan becomes automatic (#22):** it needs the game's sign-in, so it gets its own brief then.
