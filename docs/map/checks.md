# Checks

One part of the map, `docs/architecture.md`, in full. The map has the short version; a build that changes this part adds its dated note here, not in the map.

## What it is

On every pull request: no keys, the schedule check, the planner's and the planning library's type check, lint, unit tests (the library's hand-made cases included) and build (#18, #19), the planner's screen figures on a dated sample against saved answers (`tests/planner_figures.mjs`: Home's key figures, cards and figures now, every aircraft's week, maintenance and issues, and the schedule checks, on the 12 Oct report sample), the library's optimiser against plan.py's saved answer on one fixed input (`tests/optimiser_saved_answer_test.py`), the line optimiser against its saved line on the Pan Am A350 sample (`tests/line_saved_answer_test.py`, 28 Oct), the weekly report end to end on a small sample from the rehearsal's copy with each airline's money checked against the figures (`tests/report_test.py`; its PDF is the run's `weekly-report` artifact), the market definitions as `scripts/report/scan_markets.py` and gander monthly's `nl_analyze.py` load them, on that sample (`tests/market_definitions_test.py`), the capture's world scan against `gscan.py` on the same saved pages (`tests/capture_scan_test.mjs`, 21 Oct; since 23 Oct with Icelandair's saved overview page, `tests/fixtures/enterprise_overview_101_2026-10-23.html`), the capture's fleet pages on a saved fleet page (`tests/capture_fleet_test.mjs`, 22 Oct), the aircraft evaluation userscript on the tool's two saved pages, with whole runs against a stand-in for the game (`tests/aircraft_eval_userscript_test.mjs`, 27 Oct), every website page, the trip search on the library's connection rule, every airport's name and photo with the lists as data against the answers recorded before they moved out of the code (`tests/fixtures/airport_cities.expected.json`, 15 Oct), and the planner's addresses (#9: the planner's sign-in at `/planner/` and a screen's own address, `/planner/next/...` redirected to the same address under `/planner/`, `/planner/old/...` to `/planner/`; `tests/harness.py` serves `web/_redirects` as Cloudflare does). The database rehearsal (#8) runs, on a pull request, only the parts its change can affect, and every part every night on `main` (11 Nov, below): it restores last night's copy from R2 into a full local Supabase on GitHub's runner (database, data API and sign-in), applies every migration live doesn't have yet, checks the descriptions, the reference file and the planner's types straight after (11 Nov), tries the database tests, writes every captured figure the changes moved, before and after, to its `figures-moved` artifact (never the log; `database/figures_moved.py`), checks the descriptions (its `data-guide` artifact is `docs/data.md` as the copy gives it) and that `database/current/functions.sql` lists exactly the copy's functions, by schema, name and arguments, each with the definition the copy gives it, ignoring whitespace (`database/reference.py`, the definitions since 15 Oct; its `current-functions` artifact has every definition as the copy gives it), generates the planner's types again from the copy and fails if they differ from `app/planner/src/db/types.ts` (the `planner-types` artifact), builds the planner and has it sign in, read and save through `planner_save()` on the copy, open every screen at a frozen moment (the copy's latest capture plus one hour) at 1280 and 380 px with no errors and no sideways scroll, and check its addresses (`tests/planner_next_test.py`; the screenshots are the `planner-screens` artifact); then it saves through every kind of save each screen has and checks the rows each writes against the recorded ones (`tests/planner_saves_test.py`, `tests/fixtures/planner_saves.expected.json`; the answers found are the `planner-saves` artifact); the capture checks (#21, #23): one airline's saved evening of each page kind (`tests/fixtures/capture_pages_<day>.json.gz`) gives exactly its saved rows and is judged ok while the cases that must fail are judged short or broken (`database/tests/capture_checks_test.sql`), every kept page replayed is judged ok evening by evening (`capture_data_replay_test.sql`), the Systems board opens on the copy with every line marked, and a short page made on purpose shows on Today (its needs attention and its capture line) and the board, then goes; and when there were database changes, it backs the copy up and restores it into an empty database as the nightly job does, every table's rows and every permission the same. These replaced the side by sides with the old planner at the clean-up (build pull request 14; `tests/README.md`).

## Notes

**11 Nov: only the parts a change can affect, and every part every night** (to-do 233; Gitesh, 11 Nov, Main chat, brief
`docs/briefs/2026-11-11-faster-checks.md`, option E, first pull request; spec `docs/specs/2026-11-11-faster-checks.md`).
The workflow's first job, `parts`, gives `database/rehearsal_parts.py` the paths the pull request changes; it names
the parts (db, reference, types, planner, saves, briefing, samples) and `database/rehearse.sh` runs only those, through
`REHEARSE_PARTS`. A database change runs every part; a planner change the types, the planner on the copy and the saves
(about 8 to 11 minutes instead of 20 to 31); the library those and the briefing; documents nothing, and then the
rehearsal job is skipped; a path on no list every part. Migrations already on `main` that last night's backup lacks are
still applied, so the planner meets the database as live has it, but their tests aren't run again. The descriptions,
reference file and types checks run straight after the migrations, so their red shows a few minutes in. Every night at
08:43 UTC the whole rehearsal runs on `main` on the latest backup (the figures moved and the backup and restore even with
nothing to apply; no samples, no comment); a failed night shows as GitHub's failure email only, for now. The map's guide
now runs on a pull request only with the briefing (the briefing, the library or the database), and every night.
`tests/rehearsal_parts_test.py` (in `run_all.sh`) proves the grouping.
