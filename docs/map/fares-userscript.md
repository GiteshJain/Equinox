# Fares userscript

One part of the map, `docs/architecture.md`, in full. The map has the short version; a build that changes this part adds its dated note here, not in the map.

## What it is

A second userscript in Gitesh's browser in the game (since 21 Oct, manual §5; spec `docs/specs/2026-10-21-fares-userscript.md`). One button, **Apply fare plan**, after **Put on the fare plan** in Performance: it asks the database for this week's fare changes the captures haven't seen yet (since 2 Nov, version 1.3, one airline at a time: `capture_fare_actions_by_airline()` with the capture key, first the list of our airlines, then each airline in a call of its own, 10 to 15 s each, since every airline in one call, `capture_fare_actions()`, took about 70 s, past its 30 s limit and the API's 60 s; the panel says "reading this week's fare plan… Pan Am (1 of 6)"; each airline's answer is as `capture_fare_actions()` gives it: for each active airline of ours in the key's world, its `fare_ladder()` actions whose every class is on the fare plan this week, planned and not applied, with the plan rows (since 26 Oct one action per direction, matched to that direction's rows), and since 21 Oct the set-back changes, `fix`, with no plan rows, which its panel marks "set back"), shows each airline's count and asks once in its panel (no browser dialogs), then for each airline switches to it (`/app/enterprise/dashboard?select=<game id>`), opens the game's Ticket price adjustment (`/action/enterprise/flightsPrices`), maps each IATA code to the form's own airport id (`a:<id>`, never a country), and makes each change as one GET of that form (`adjust=true`, the two airports, any service profile, + or −, the percent, baseline default price, the classes), checking the answer's Changed Airport Pairs for that From and To and each class, 2 seconds apart. It stops at the first problem and says which change and why: an airport missing from the form, an answer without the expected rows, an HTTP error, the session lost, or the game showing another airline open (its selected-airline cookie, where the browser lets the page read it). What's done stays done: run again, it reads only what's still unseen (changes made since the last capture show as unseen until then; setting a level twice does no harm). Its panel shows progress ("Pan Am: 12 of 50"), a **Stop** button, and at the end each airline's count of changes made. Its state is kept in `sessionStorage`, as the capture's, so the page loads it makes carry on where it was. It reads only the fares page and its answers and changes only prices; never on a schedule. The next capture ticks the changes off on the fare plan (`fare_plan_status()`).
