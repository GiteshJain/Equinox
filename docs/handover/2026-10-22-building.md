## How this chat works (habits worth keeping)
- **Helpers in their own clones** (`git clone … /home/claude/<name>-build`), never the shared `/home/claude/equinox`.
  Spec on its own branch first; the helper opens the PR and **stops** (no polling).
- **Waiting on checks:** one background shell loop on the PR head's check runs (`gh api …/commits/<sha>/check-runs`,
  every 60 s until none pending), which costs nothing while it waits.
- **A PR whose checks never start** is usually in conflict with `main` (`mergeable_state: dirty`): merge `main` into it
  and resolve.
- **After merging a database PR:** apply the migration exactly as the file is written (comments inside function bodies
  count; stripping them makes live differ from the repository), set its version in
  `supabase_migrations.schema_migrations`, and compare function fingerprints (md5 of `pg_get_functiondef` with
  whitespace removed) with `database/current/functions.sql`. For a very large file, Gitesh runs it in the SQL editor
  (raw GitHub link) and the chat records and checks it.
- **Rehearsal failures seen today and their fixes:** regenerated `functions.sql`, `types.ts` or `data.md` (commit the
  run's artifact); the map's guide examples must be a single backticked call; `docs/data.md` must match the database's
  descriptions (another chat hand-edited a line once; a description change needs a migration).
- **Style:** project instructions set a playful, flirty assistant voice for chat replies only; documents, code and
  briefs stay neutral.
