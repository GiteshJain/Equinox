# Build spec: the automatic jobs and their warnings (#13 build, pull request 7) — 11 Oct 2026

**Why:** step 7 of the build order (`docs/design/2026-10-09-data-model.md` §10), as decided in the jobs brief
(`docs/briefs/2026-10-09-jobs.md`, option B, Claude's call at Gitesh's request). The daily record (pull request 6)
needs a fallback for evenings without a complete capture; the capture tables need their clean-ups; #16 needs the
monthly archive before 1 Dec; and a job that fails must show on the planner's Home.

**Outcome when done:**
- `pg_cron` runs, inside the database: the 10:00 UTC snapshot fallback and the clean-ups. No key leaves the database.
- `backup_runs` lives on as a view over `job_runs`, so the nightly backup keeps working whatever the deploy order.
- The monthly archive runs as a step of the nightly backup job in `equinox-backups`, deleting only through the
  guarded `private.archive_delete()`.
- The planner's Home warns when a backup or snapshot is late, the month's archive hasn't run by the 3rd, or any job's
  last run failed.

## What to build
The design is the specification: §3.11, §3.12 (`backup_runs`), §7 (snapshots, clean-ups, the archive, `job_runs` and
the planner), and the jobs brief. Where they disagree with this spec, stop and say so.

### 1. In `Equinox`
- **`pg_cron`** switched on, with two jobs:
  - **10:00 UTC:** the snapshot fallback for the capture day just ended, if none was taken (`complete = false`,
    `source = 'fallback'`, cash from the latest balance before it), plus filling any missed day since the tables went
    live (§7 "Filling a gap later").
  - **10:20 UTC:** the clean-ups: `game_capture_raw` older than 14 days (moved out of the capture, which does it on
    every page today), and `game_statement` lines older than 14 days only once their flights are in `game_flights`
    (the job checks counts first). **The statement clean-up ships switched off** behind a setting
    (`settings`: `statement_cleanup_enabled` = false); the Building chat switches it on after checking on live.
  - Each run writes one `job_runs` row (start, finish, ok/failed, note).
- **`job_runs` takes over `backup_runs`:** its rows move into `job_runs` (job `backup`, details as §3.11), the table is
  renamed `backup_runs_before_13`, and `backup_runs` becomes a view of today's shape with an `instead of insert`
  trigger that turns the backup job's row into a `job_runs` row (§3.12). The planner's Check → Capture board and Home
  keep reading `backup_runs` as today.
- **The archive's database side:** `private.archive_manifest(month, table)` (row count, checksum of the rows in key
  order, the table's layout and latest migration version) and `private.archive_delete(month, table, expected_count,
  checksum)`, which refuses a table not listed in §7, a month inside the kept window (one full calendar month; 12 for
  `change_log`), a count or checksum that no longer matches, and `game_flights` for a month whose days aren't all in
  `route_days`. Both callable only by `postgres`. A function the archive step calls to list what's due.
- **Home's warnings** in the planner (`web/planner/index.html`, a few lines in Home only): from `job_runs` (staff
  read it) and `backup_runs` — the last good backup more than 30 hours old (as today), the latest snapshot more than 30
  hours old, the month's archive not run by the 3rd, any job's last run failed (naming the job and its note).

### 2. In `equinox-backups` (a second pull request, same build)
- **The archive step** in the nightly job, on the first run on or after the 1st, retried each night until done (§7):
  for each table and month due, export the rows to `archive/<table>/<YYYY-MM>.csv.gz` with the manifest beside it,
  upload to R2 and attach to the month's GitHub release, read both copies back and check count and SHA-256, then call
  `private.archive_delete(...)`. Each table-month writes one `job_runs` row (job `archive`).
- On a pull request (dry run): export and check, upload to `test/` and delete it again, and call `archive_delete` with a
  wrong count to prove it refuses. Nothing is deleted.
- The README's "Restoring → Just the planner after a bad save" changes: the planner now lives in the tables; undo a
  bad change with `private.restore_row()` from `change_log`, or restore the tables from a copy. (Follow-up from pull
  request 9.)

### 5. Proving it
- **Rehearsal (`Equinox`):** `pg_cron` jobs exist with the right schedules; calling each job's function directly on the
  copy does its work and writes its `job_runs` row; the fallback takes a snapshot for a day without one and leaves a day
  that has one alone; the raw-page clean-up deletes only pages older than 14 days; with the setting off, no statement
  line is deleted, and with it on, only lines whose flights are in `game_flights`; `backup_runs` reads exactly as
  before the migration and an insert into it lands in `job_runs`; `archive_delete` refuses a month in the kept window,
  a wrong count, a wrong checksum and an unlisted table, and deletes exactly the rows when everything matches.
- **Planner checks:** Home shows each warning when its condition holds in the stand-in, and none when all is well.
- **`equinox-backups` dry run:** the archive step exports, checks and uploads to `test/`, and `archive_delete` refuses
  the wrong count.
- Everything earlier still passes, real saves included.
