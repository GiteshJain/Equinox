# Build spec: the new planner's Review screen, and the plan card's service check (#18 build, pull request 10) — 14 Oct 2026

**Why:** steps 10 and 11 of the build order (`docs/design/2026-10-12-planner-app.md` §13), done as one pull request (Gitesh,
14 Oct). Review is each airline's money: its card, its profit day by day, the cash forecast, route and aircraft profit,
fare changes and the fare plan, and manual entry when a capture fails. Home to Check set the pattern: same features and
look as the old screen, every figure from its one home, proven side by side.

The game runs again since 14 Oct, with game changes made in the old planner only; **its code stays frozen (manual §1):
nothing in `web/planner/` changes.** Anything found while playing is fixed in the new planner, which is why the plan
card's service check (part 2) is here.

**Note on names:** the old planner's nav button "Review" opens its `finance` view (`renderFinance`). That is what this
pull request rebuilds.

## Part 1: Review
**Outcome when done:** `/planner/next/review` and `/planner/next/review/<airline code>` do everything the old Review
does, on a phone too:
- **The group today:** one row per airline as the old board has it, **with no group total and no surplus figure**
  (manual §5: each airline is its own business; §3: the surplus figure is retired). If the old board shows either, leave
  it out and list the difference in the pull request;
- **the airline cards:** profit a day (or why there's none yet), per aircraft, return on fleet, payback, funds a new
  aircraft every, fleet, flights a day, 7-day load, next order, the sparkline; choosing one opens its page;
- **the airline page:** the profit chart for the last 14 intervals with its average, the table of reported days, the
  cash forecast, route profit, aircraft profit, fare changes and the fare plan;
- **manual entry:** cash and fixed costs for today, loads by hand for a day (typed, or pasted from the game's load
  table and read), and the 7-day nightly log.

  The airline in the address. At 380 px the cards stack and nothing scrolls sideways; wide tables scroll inside their

## Part 2: the plan card's service check
**Why:** on 13 Oct, 22 of 37 round trips on the new plan cards had service codes S1, S2, S3 given by position on the card
instead of by the route's distance, and were fixed by hand (Gitesh).

- **In the library (`lib/rules/`):** `checkCard` flags any leg whose service code isn't the one its route's distance
  calls for (`service.ts`'s `profileFor` on `service_profiles`, Ryanair's own row included), naming the leg, the code
  given and the code wanted. `CardLeg` gains the leg's service code. If the service profiles aren't in the rules input,
  add them to `rules_input()` (same arguments, so it can be applied from the chat) rather than making each caller pass
  them. Cases for: the right code, a wrong code, a leg with no code, Ryanair.
- **Where it shows:** the plan-card check the other chats run (the library's command, `check a plan card`), and on the
  new Tails' plan cards as an issue on the leg.
- **Proof:** the side by side doesn't cover it (the old planner has no such check). Unit cases, and one rehearsal step
  that runs the command on a plan card from last night's copy and lists what it flags (a finding, not a failure).

## Checks
- **Unit tests:** the cards' wording when a figure is missing, the load paste reader (the old `parseLoadPaste` cases),
  the chart's intervals, the service check's cases.
- **In the rehearsal, `tests/review_side_by_side_test.py`,** at a frozen moment, both planners as the test staff user:
  for every airline, the card, the page's chart and table, the cash forecast, route profit, aircraft profit, fare
  changes and the fare plan equal the old ones' (apart from the group total and surplus, listed). Real saves in the new
  planner: cash and fixed costs, loads typed, loads pasted from a saved sample with a day marked complete. Each writes
  exactly the old planner's rows, and the old planner then shows the same. A preview address shows Review and sends no
  write. 380 px with screenshots (`review-screens` artifact).
- `tests/planner_next_test.py`: Review is no longer a placeholder.
- Keep the run under 30 minutes; sample if needed and say so.

## Rules for the helper
- Follow `CLAUDE.md`. Read `.claude/skills/supabase-postgres-best-practices/SKILL.md` for any migration. Reuse the
  earlier screens' code (`app/planner/src/`) and their side-by-side tests.
- **Work lean:** check on GitHub runs every few minutes rather than continuously, and don't read beyond what the build
  needs.
- **Never connect to the live database or use the Supabase connector tools.** Don't change `web/planner/` or
  `web/assets/`. Any migration adds only (no drops, no changed function arguments).
- If a figure differs from the old Review, find the cause; report a real difference as a finding.
- Work on branch `review`, open the pull request with the REST API, and don't merge.

## Done when
Every proof is `ok` and the deliberate failure was seen to fail, then removed. The pull request says what changed, the
run time, any finding (including what the service check flags on last night's cards), the steps after "merge" (and
whether any migration can be applied from the chat), and how to roll back.
