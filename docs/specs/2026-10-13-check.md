# Build spec: the new planner's Check screen (#18 build, pull request 9) — 13 Oct 2026

**Why:** step 9 of the build order (`docs/design/2026-10-12-planner-app.md` §13). Check is the daily look at how the
network is doing: what the capture collected, where to grow, which aircraft are due their one-week check, which cabins
don't fit their markets, whether the planner matches the game, and the day's loads. Home (5), Routes (6), Tails (7) and
Hubs (8) set the pattern: same features and look as the old screen, every figure from its one home, proven side by side.
The game is paused and the old planner frozen (manual §1): **nothing in `web/planner/` changes.**

**Note on names:** the old planner's nav button "Check" opens its `review` view (`renderReview`); its "Review" button
opens `finance`. This pull request rebuilds the old **Check** (`renderReview`). Review (`renderFinance`) is pull request
10.

**Outcome when done:** `/planner/next/check` does everything the old Check does, on a phone too, with its boards in the
same order, each folding open and shut, with **Collapse all** and **Expand all**:
- **Capture:** what the capture collected for each airline and when, with reload;
- **Growth:** which airlines can order now, main hubs' progress (hubs first), the next move for each airline and when
  each order queue runs dry;
- **Aircraft checks:** the one-week checks due (with the aircraft's issues and its routes' load signals), the ones
  coming up by date, and how many are done; **Mark checked** (Gitesh does this himself; Claude never does);
- **Cabins:** each aircraft's cabin against what its markets want, **Log refit**, **Keep as is**, and the kept ones with
  undo;
- **Game check:** **Check against the game** for every airline with a game link, the differences and the game's flights
  missing from the planner, **Fix from the game** (one or all) and **Add** a flight from the game;
- **Daily load report:** a day at a time (‹ ›), every departure by airline with its captured loads by class, the day's
  summary.

## What to build
The design is the specification: §2, §4 to §8, §9 (Check's row), §10, §14. The old Check is the reference:
`renderReview`, `captureBoard`, `growthBoard`, `hubProgressHtml`, `tailChecks`, `tailIssues`, `patterns`, `cabinsBoard`,
`cabinFit`, `renderGameCheck`, `runGameCheck`, `gcDetail`, `gcModal`, `importFlight`, `flightsOn`, `capLine` in
`web/planner/index.html`. Search for them; don't read the file whole. Where the design and this spec disagree, stop and
say so.

### Data and figures
- **From the database's figures (§8):** capture from `capture_status()`; growth from `growth_signals()`,
  `hub_progress()`, `airline_cards()` (can order now) and `cash_forecast()`; loads from the captured loads (`game_loads`)
  through an existing function where one fits.
- **From the library (`lib/rules/`):** the check dates, the aircraft's issues (Tails' `tailIssues`), the cabin fit, and
  the game comparison (the same code Tails' filing uses).
- **Anything the old screen works out that has no home yet** goes to the library (with cases) or the database's figures
  (a new `fig_*` with a staff function), not the screen. Add only; avoid migrations that drop or change a function's
  arguments.
- **The old planner's lists in code** (for example `MAIN_HUB`, `SPEND_ORDER`, `REFIT_M`): use the database's home where
  one exists; where none does, say so in the pull request rather than copying the list into the screen.

### Saving (one action each, through `planner_save()`, all or nothing)
Mark checked; log a refit (the aircraft's cabin and its `spending_log` row); keep as is and undo; fix one or all from
the game (the legs' times, as the old `gcfix` writes them); add a flight from the game (as `importFlight` does). Each
writes exactly the rows the old planner writes. Clashes show the shell's message.

### The screen
- `app/planner/src/screens/check/`, shared parts from `src/ui/`. Address `/planner/next/check`, with the load report's
  day in the address (`?day=YYYY-MM-DD`). Links to an aircraft or a route open Tails and Routes.
- At 380 px the boards stack and nothing scrolls sideways; wide tables scroll inside their own box.
- `data-figure` names on every figure.

## Checks
- **Unit tests:** the check status (due, upcoming, done, and back to due when a schedule changes), the cabin fit and keep
  rule, the game comparison (same, different, missing, extra, game error), the load report's summary.
- **In the rehearsal, `tests/check_side_by_side_test.py`,** at a frozen moment, both planners as the test staff user:
  every board equals the old one's (capture, growth, aircraft checks, cabins, the load report on each of the last 7
  days). With `/api/game-schedule` answered from saved samples (reuse Tails'): the game check's results equal the old
  one's, and **fix one**, **fix all** and **add a flight** in the new planner write exactly the old planner's rows.
  Mark checked, log a refit, keep as is and undo each write only their rows, and the old planner then shows the same.
  A preview address shows Check and sends no write. 380 px with screenshots (`check-screens` artifact).
- `tests/planner_next_test.py`: Check is no longer a placeholder.
- Keep the run under 30 minutes; sample if needed and say so.

## Proving it
- `bash tests/run_all.sh` passes; the rehearsal passes with every step `ok`; screenshots attached.
- **A deliberate failure,** seen to fail then removed: an aircraft's one-week check falls due 6 days after its schedule
  starts instead of 7 (a unit test and the side by side must go red).

## Rules for the helper
- Follow `CLAUDE.md`. Read `.claude/skills/supabase-postgres-best-practices/SKILL.md` for any migration. Reuse Home's,
  Routes', Tails' and Hubs' code (`app/planner/src/`) and their side-by-side tests.
- **Work lean:** check on GitHub runs every few minutes rather than continuously, and don't read beyond what the build
  needs.
- **Never connect to the live database or use the Supabase connector tools.** Don't change `web/planner/` or
  `web/assets/`.
- If a figure differs from the old Check, find the cause; report a real difference as a finding.
- Work on branch `check`, open the pull request with the REST API, and don't merge.

## Done when
Every proof is `ok` and the deliberate failure was seen to fail, then removed. The pull request says what changed, the
run time, any finding, the steps after "merge" (and whether any migration can be applied from the chat), and how to
roll back.
