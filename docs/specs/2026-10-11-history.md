# Build spec: the daily history and the world-scan tables (#13 build, pull request 6) — 11 Oct 2026

**Why:** step 6 of the build order (`docs/design/2026-10-09-data-model.md` §10), after the switch-over. Decision #15
keeps a daily record of each airline and route for good, and #16 keeps scan summaries for good while the detail is
archived. The world-scan tables were moved here from pull request 3 (9 Oct), so the scan's functions change once.

**Outcome when done:**
- `airline_days` and `route_days` hold one row per airline per capture day and per route, direction and UTC day,
  filled back as §9 step 4 says, and taken automatically when a world's evening capture is complete.
- The world-scan tables are renamed and split (§3.9), with the airport and market summaries kept for good.
- Two captures on the same UTC date no longer leave a balance whose time and figures come from different captures.
- The planner, website, capture and scripts behave as before; the weekly report's scan data comes out the same.

## What to build
The design is the specification: §2 ("What a day means"), §3.9, §3.10, §7 ("The daily snapshot"), §9 step 4, §10
row 6, §11 choice 2. Where the design and this spec disagree, stop and say so.

### 1. In this pull request
- **`airline_days` and `route_days`** exactly as §3.10, with RLS, grants and descriptions. Not logged by the change
  log (§6).
- **The snapshot** (`private.take_snapshot(world, day)`), called from `capture_ingest` after the page that completes a
  world's capture for the day (completeness as pull request 3 defined it). Point-in-time figures are fixed when taken
  and replaced by a later complete capture of the same day; flows for the two days before are recomputed each run
  (§7). It writes nothing to `job_runs` yet (that table exists; record a `snapshot` row there if it's simple, else
  leave it to pull request 7, which adds the 10:00 UTC fallback and the warnings).
- **Backfill** (§9 step 4): `route_days` from `game_flights` since 6 Oct; `airline_days` from 29 Sep (cash from the
  stored figures, then `game_balance` from 7 Oct; flights from 6 Oct; the fleet from delivery dates; weekly departures
  from each rotation's launch date, marked `source = 'backfill'`). Since the switch-over the old `planner_state` is
  frozen: take the stored cash for 29 Sep to 6 Oct from `cash_entries` (where pull request 4 put it).
- **World scans** (§3.9): `game_snapshots`, `game_snapshot_airlines` and `game_snapshot_airports` become
  `game_scans`, `game_scan_airlines` (totals), `game_scan_schedules` (each airline's schedule) and
  `game_scan_airports`, with ids; every airline a scan sees becomes an `airlines` row by game ID (§3.9). The old names
  must keep working for anything not changed here, or everything that uses them changes in this pull request:
  `ingest_snapshot`, `export_for_report`'s scan kinds, `export_planner_data`, `export_repo_bootstrap`, and
  `scripts/scanner/gscan.py`, `scripts/report/pull.py` if they name tables. Their outputs stay the same.
- **Scan summaries** (choice 2: totals per airport and per market, kept for good): `scan_airline_airports` built when
  a scan finishes, and filled for every scan already stored; `scan_airline_markets` sent by the report script, which
  owns the market definitions: add the ingest kind and the script's call, and say in the pull request how the existing
  scans' market summaries get filled (the Building chat can run the script once after merge if it can't be done in
  SQL).
- **The two-captures bug** (found by pull request 3): `game_balance` and `game_pnl` keep the first capture's
  `captured_at` while a second capture on the same UTC date overwrites the figures. Make the figures and their time
  always come from the same capture; the cash forecast and `capture_cash` read the latest one. Add a test.
- **Descriptions** on everything new, and `docs/data.md` regenerated.

### 4. Proving it (the rehearsal, on last night's copy)
- **Backfilled days match what's known:** each airline's cash on the days the old planner stored, flights per day from
  `game_flights`, and the fleet on today's date against `aircraft`.
- **The snapshot on a complete capture:** replaying the copy's last evening of capture pages takes exactly one
  snapshot when the last airline's last page arrives, not before; a second complete capture the same day replaces the
  point-in-time figures.
- **Scans:** the scan outputs of `export_for_report`, `export_planner_data` and `export_repo_bootstrap` are the same
  before and after; `ingest_snapshot` stores a hand-made small scan into the new tables and its airport summaries.
- **Two captures on one UTC date:** a test where the second capture's figures and time both win.
- Everything earlier still passes, real saves included.
