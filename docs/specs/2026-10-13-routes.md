# Build spec: the new planner's Routes screen (#18 build, pull request 6) — 13 Oct 2026

**Why:** step 6 of the build order (`docs/design/2026-10-12-planner-app.md` §13). Routes is where flights are planned:
every route in the research, and on each one its frequencies, their times, days, aircraft and flight numbers, checked
against every scheduling rule at both ends. Home (pull request 5) set the pattern: same features and look as the old
screen, every figure from its one home, proven side by side. The game is paused and the old planner frozen (manual §1):
**nothing in `web/planner/` changes.**

**Outcome when done:** `/planner/next/routes` does everything the old Routes does, on a phone too:
- **the list:** one airline at a time; search by destination; filter by base, demand stars, market, distance range and
  active only; sort by stars, distance up or down, destination, or load; each row with its stars, distance, market,
  frequencies and 7-day load; **Add route**; **Remove unflown routes**;
- **a route:** its header (stars, airline, market, distance, the two UTC offsets, estimated block on the market's
  aircraft, the market's plan, cabin and price, service profile, the hub's banks); **edit route** (stars, market,
  distance, city, the two offsets); **remove route**; the next free flight-number pair;
- **its frequencies:** each with outbound and return times (local or UTC, as the header toggle says, with the other
  shown small), block times (typed or estimated), days, aircraft, flight numbers, per-flight loads, and every check:
  bank fit at both ends, connections, short or tight turns, the aircraft's position, night bans, a flight number used
  twice, the second-daily gap; add, change and delete a frequency;
- **the route pop-up** opened from Home's map, with the route's figures, its frequencies and its load pattern.

## What to build
The design is the specification: §2, §4 to §7, §9 (Routes' row), §10, §14. The old Routes is the reference:
`renderRoutes`, `routeRows`, `renderRouteDetail`, `renderRouteEdit`, `renderAddRoute`, `renderFreq`, `routeModal`,
`computeFreq`, `routeSummary`, `nextPair`, `waveAt`, `banPills`, `flightClashes`, `lfChip`, `loadStats` in
`web/planner/index.html`. Where the design and this spec disagree, stop and say so.

### 1. Data
- **The list** loads one airline's routes at a time from the tables (`routes` with their overrides, markets, service
  profiles), not the whole research at start. The flown routes are in the start already (`rules_input(…, 'flown')`).
- **Loads:** per route and **per flight** over 7 days from the database. Extend `route_loads()` with each flight's
  figures (by flight number) rather than working them out on the screen.
- **A frequency** is a rotation with its outbound (leg 1, hub to destination) and return (leg 2). Times are typed in
  local time at each end and stored in UTC (`flight_legs.dep_utc_min`, `days_utc`, `block_min`), as #13's design §4
  says; the return's day follows the old planner's rule (the first departure within 24 hours of the outbound's
  landing). A typed arrival sets the block time; with none, the library's estimate is used and marked "est".
- **All checks from the library** (`lib/rules/`): block estimates, bank fit (`banks`), connections at both ends
  (`connections`), turns and positions (`turns`, `aircraftWeek`), night bans, flight numbers used twice, the
  second-daily gap and the next pair (`schedule`). Add to the library only what's missing, with cases, never on the
  screen.

### 2. Saving (one action each, through `planner_save()`, all or nothing)
- **Add route:** a `routes` row (the airline, hub, destination; city and distance from the airport list when known;
  market). **Edit route:** the override columns (`stars_override`, `market_override_id`, `market_cleared`,
  `distance_override_km`, `city_override`), as the old planner's `routeEdits` map to them. **Remove route** and
  **Remove unflown routes:** `removed` and `removed_note`, never a delete (Reference restores them, pull request 12).
- **A frequency:** add (a rotation and its two legs, using `planner_save()`'s `as` and `from`), change (the legs'
  times, days, aircraft and numbers, and the rotation), delete (the legs, then the rotation). Each is one action.
- **A UTC offset:** the old planner keeps the local times when an offset changes. So changing one is one action that
  sets `world_airports.utc_offset_override` and re-times every leg touching that airport to keep its local times. The
  screen first lists the flights that move and asks to confirm in the page (never a browser dialog).
- **Clashes:** the shell's message, as on Home.

### 3. The screen (`app/planner/src/screens/routes/`)
- **The look** of the old Routes, from the shared parts in `src/ui/` (add to them rather than copying).
- **Addresses:** `/planner/next/routes` (the list, its filters in the address so a link reopens them) and
  `/planner/next/routes/<airline code>/<hub>-<destination>` (a route). Home's map and "Routes to fix" open these
  instead of the old planner.
- **Phones:** at 380 px the list becomes cards, a frequency's two legs stack, and the time fields stay usable; nothing
  scrolls sideways.
- **Every figure** carries `data-figure` names, for the side by side.

### 4. Checks
- **Unit tests:** local and UTC times both ways, including across midnight and the return's next day; the filters and
  sorts; the offset re-timing (local times kept); a frequency's save payload.
- **In the rehearsal, `tests/routes_side_by_side_test.py`,** on last night's copy at a frozen moment, both planners
  signed in as the test staff user:
  1. for every airline, the list (rows, order under each sort, each filter's count) equals the old one's;
  2. for every flown route, the header and every frequency line (times both ways, block, est, days, aircraft, numbers,
     loads, every pill and its words) equal the old one's;
  3. real saves in the new planner: add a route, edit its stars and market, add a frequency with times and days, change
     its time, delete it, remove the route, change an offset on an airport one flight uses. Each writes exactly its
     rows, logged as planner with the tab's ID; the old planner then shows the same route and frequency, with the same
     times;
  4. a preview address shows Routes and sends no write;
  5. at 380 px: no sideways scroll, no errors; screenshots of the list and a route at 380 and 1280 px, new and old, as
     the run's `routes-screens` artifact.
- `tests/planner_next_test.py`: Routes is no longer a placeholder.
- The time limit stays 30 minutes; say how long the run took. If the side by side grows long, sample routes rather
  than dropping a kind of check, and say so.

### 5. Docs, in the same pull request
- **`docs/planner-guide.md`:** Routes in the new planner. **The map:** Routes' sources and saves. Claude copies it into
  the project after the merge. **`tests/README.md`**, **`docs/data.md`** (regenerated by the rehearsal).

## Proving it
- `bash tests/run_all.sh` passes; the rehearsal passes with every step of the new test `ok`; the screenshots are
  attached.
- **A deliberate failure** is seen to fail, then removed: the return's day taken as the outbound's day (a unit test and
  the side by side must go red).

## Rules for the helper
- Follow `CLAUDE.md`. Read `.claude/skills/supabase-postgres-best-practices/SKILL.md` for any migration. Read Home's code
  (`app/planner/src/screens/home/`, `src/ui/`, `src/data/`) and `tests/home_side_by_side_test.py` first: reuse them.
- The old planner is one large file: search for the functions named above rather than reading it whole.
- **Never connect to the live database or use the Supabase connector tools.** Test by pushing and reading the *checks*
  and *Database rehearsal* results. Docker is available here.
- **Don't change `web/planner/` or `web/assets/`.**
- If a figure differs from the old Routes, find the cause; if it's a real difference in rules or data, report it as a
  finding with the figures rather than bending it to match.
- A migration that drops or replaces a function's arguments needs Gitesh to run it: say so in the pull request, and
  avoid it where a new function or an added optional argument would do.
- Work on branch `routes`, open the pull request with the REST API (GraphQL is blocked), and don't merge.

## Done when
- Every proof above is `ok`, and the deliberate failure was seen to fail, then removed.
- The pull request says: what changed; the rehearsal's run time; any finding; the steps after "merge" in order; how to
  roll back; anything outside the repository that needs a follow-up.
