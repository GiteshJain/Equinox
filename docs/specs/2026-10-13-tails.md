# Build spec: the new planner's Tails screen and filing (#18 build, pull request 7) — 13 Oct 2026

**Why:** step 7 of the build order (`docs/design/2026-10-12-planner-app.md` §13). Tails is every aircraft: what it flies
each week and how hard it works, the aircraft on order with their plan cards, and **filing** an arrived aircraft into
the planner from its plan card after checking it against the game. Home (pull request 5) and Routes (6) set the
pattern: same features and look as the old screen, every figure from its one home, proven side by side. The game is
paused and the old planner frozen (manual §1): **nothing in `web/planner/` changes.**

**Outcome when done:** `/planner/next/tails` does everything the old Tails does, on a phone too:
- **the list:** one airline at a time; filters for base, type and Flying / No flights / Needs a look; each aircraft's
  legs a week, block hours a day, maintenance (usable ground time against the need, with the hours on hover or tap),
  routes; **Add a tail**; remove;
- **an aircraft:** its header (type, cabin, legs a week, block hours a day, gap target, minimum turn, big gaps,
  maintenance) and editable fields (registration, type, cabin, base, status), its week of legs in order with turns and
  gaps, and every issue (`tailIssues`);
- **deliveries:** aircraft on order or arrived and not yet scheduled, with status filters, each with its plan card
  (title, base, legs with flight numbers, route, times, block, service);
- **filing:** for an arrived aircraft, **File into planner** reads the airline's schedule from the game (the existing
  `/api/game-schedule` function and the airline's saved game link), compares each plan-card leg, and either files at
  once when everything matches or shows the differences and lets Gitesh file with the plan card's times or the game's.
  Filing makes the aircraft active, logs its first cabin fit, and creates a frequency for each outbound and its return,
  as the old `filePlan` does;
- **the aircraft pop-up** opened from Home and Routes.

Home's "File into planner" and "Open fleet ›" then open here instead of the old planner.

## What to build
The design is the specification: §2, §4 to §7, §9 (Tails' row), §10, §14. The old Tails is the reference:
`renderTailsWithDeliveries`, `renderTailsCore`, `renderTailDetail`, `tailIssues`, `tailChecks`, `renderDeliveries`,
`deliveryRows`, `planCard`, `planModal`, `checkBeforeFile`, `fileCheckModal`, `fileFromCheck`, `filePlan`,
`importFlight`, `tailModal`, `maintPill`, `DEFAULT_CABIN`, `cabinCostM` in `web/planner/index.html`. Where the design and
this spec disagree, stop and say so.

### Data and figures
- Aircraft, types, cabins, plan cards and their legs from the tables. Every planning figure (legs a week, block hours,
  turns, gaps, maintenance, issues, positions) from the library; add only what's missing, with cases.
- **The order cabin and its cost** come from the database's one home for it (`private.fig_order_cabin`, design §16):
  give the screen a staff function for it rather than repeating the old `DEFAULT_CABIN` in the screen.

### Saving (one action each, through `planner_save()`, all or nothing)
- Add, edit and remove an aircraft (remove = `retired_on`, never a delete).
- **Filing** is one action: the aircraft's status, its first cabin fit in `spending_log`, and every rotation with its two
  legs (`as` and `from`), times converted from local to UTC with the old planner's next-day rule (Routes' code, reused).
  If the plan card takes the game's times, the plan card's legs change in the same action.

### The screen
- Shared parts from `src/ui/`; Routes' frequency code for the legs. Addresses `/planner/next/tails` and
  `/planner/next/tails/<registration>`.
- At 380 px the list becomes cards and nothing scrolls sideways.
- `data-figure` names on every figure.

### Checks
- **Unit tests:** the filters, the delivery status, the plan-card comparison (same, different, missing, game error),
  filing's payload (frequencies paired as `filePlan` pairs them).
- **In the rehearsal, `tests/tails_side_by_side_test.py`,** at a frozen moment, both planners as the test staff user:
  every airline's list and every aircraft's page equal the old ones'; the deliveries board equals the old one;
  **filing** one arrived aircraft from its plan card in the new planner (with `/api/game-schedule` answered from a saved
  sample, both "matches" and "differs, use the game's times") writes exactly the old planner's rows for the same card,
  and the old planner then shows the aircraft flying the same frequencies; add, edit and remove a tail write only their
  rows; preview read-only; 380 px with screenshots (`tails-screens` artifact).
- `tests/planner_next_test.py`: Tails is no longer a placeholder.
- Keep the run under 30 minutes; sample if needed and say so.

### Docs, in the same pull request
`docs/planner-guide.md` (Tails in the new planner), the map, `tests/README.md`, `docs/data.md` (regenerated).

## Proving it
- `bash tests/run_all.sh` passes; the rehearsal passes with every step `ok`; screenshots attached.
- **A deliberate failure**, seen to fail then removed: filing pairs a return with the wrong outbound (flight numbers 2
  apart instead of 1).

## Rules for the helper
- Follow `CLAUDE.md`. Reuse Home's and Routes' code (`app/planner/src/`) and their side-by-side tests.
- **Work lean:** check on GitHub runs every few minutes rather than continuously, and don't read beyond what the build
  needs. The old planner is one large file: search for the functions named above.
- **Never connect to the live database or use the Supabase connector tools.** Don't change `web/planner/` or
  `web/assets/`. Avoid migrations that drop or change a function's arguments.
- If a figure differs from the old Tails, find the cause; report a real difference as a finding.
- Work on branch `tails`, open the pull request with the REST API, and don't merge.

## Done when
Every proof is `ok` and the deliberate failure was seen to fail, then removed. The pull request says what changed, the
run time, any finding, the steps after "merge" (and whether any migration can be applied from the chat), and how to
roll back.
