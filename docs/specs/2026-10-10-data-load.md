# Build spec: load the planner's data, and the adapter's read side (#13 build, pull request 4) — 10 Oct 2026

**Why:** step 4 of the build order in `docs/design/2026-10-09-data-model.md` (§10). The tables from pull request 2 are
empty apart from the reference rows. This pull request fills them from today's planner storage, and adds the functions
that build today's planner JSON back from the tables, so the next pull request can prove old and new are the same
before anything reads the new tables for real.

**Outcome when done:**
- The planner's data is in the tables: airports and countries, aircraft types and cabins, markets, service profiles,
  bases, buy lists, settings and world rules, aircraft, routes, rotations and flight legs, plan cards, to-dos, the logs,
  interline, monthly checks, dismissals, typed cash and typed loads.
- `planner_state_get()` returns today's `planner_state` JSON, `planner_state_version()` its save time, and
  `planner_loads_get()` today's loads documents, all built from the tables.
- The capture pairs each flight's money with its loads, now that airports have time zones.
- Nothing reads these functions yet. The planner, website, capture and scripts behave exactly as before.

## What to build
The design is the specification: §2, §3.2 to §3.7 (columns, and the first rows of §3.7), §4 (flights: a frequency
becomes a rotation and two legs, UTC weekdays, the return-day rule, block time, flight numbers), §8 (the getter, cash
and loads), §9 step 3 (what is loaded from where) and "Proving old and new are the same", §10 row 4. This spec says
what belongs in this pull request and how to ship it. Where the two disagree, stop and say so in the pull request.

### 1. In this pull request
- **The loader, `private.load_planner(world_id)`:** reads `planner_state`, `planner_loads`, `planner_data`,
  `site_content.mct`, `planner_meta.growthRules` and the planner's code constants (copied into the migration as data,
  with a comment naming where each came from in `web/planner/index.html`), and writes the tables as §9 step 3 says.
  - It runs as `migration` with the change log off (§6, §9).
  - **It can be run again:** a second run brings the tables back in line with today's `planner_state` (inserting,
    updating and deleting rows as needed) without changing ids that already exist. Pull request 5 runs it once more
    just before it starts mirroring saves.
  - Anything in the old JSON a table has no column for goes into that row's `extra`, so nothing is dropped. List in
    the pull request every key that ended up in `extra` (expected: none).
  - The six home airports already exist as code-only rows (pull request 2): fill them in, don't insert twice.
- **The getters:** `planner_state_get(world_id default null)`, `planner_state_version(world_id default null)` and
  `planner_loads_get(world_id default null)` as §8, `security invoker`, refusing anyone who isn't staff, granted to
  `authenticated` only. The view `capture_cash` (§3.12) that the getter's cash comes from.
- **Matching after the airports load:** run `private.capture_refresh(<Gander>)` once the airports have time zones, so
  the money-only and loads-only rows the capture has written since pull request 3 pair up. Fill `game_events.due_at`
  and the `route_id` and `aircraft_id` columns of `game_flights` the same way. From then on each capture matches as it
  goes.
- **Descriptions** on everything new, and `docs/data.md` regenerated.

### 2. Not in this pull request
- `planner_state_put`, `save_loads` on the tables, `planner_item_put`/`_delete`, the side-by-side trigger and the
  nightly comparison (pull request 5).
- `airline_days`, `route_days`, the scan tables (6); jobs (7); website and scripts (8); the switch-over (9).
- No change to the planner, the website, the capture's userscripts or `planner_state`.

### 3. How to ship
- **One migration** that adds the functions and view and runs the load and the matching. It must run as one piece and
  apply cleanly on last night's copy. Say in the pull request how long it takes.
- **If anything removes or revokes** something that exists, it goes in a short separate file for Gitesh to run
  (manual §1). Expected: nothing.
- It will be applied when no capture is running.

### 4. Proving it (the rehearsal, on last night's copy)
- **The getter equals today:** `planner_state_get()` equals `planner_state.json`, and `planner_loads_get()` equals
  every month of `planner_loads`, with only the differences §9 allows (key order; a missing key equals `null`;
  numbers by value; flight numbers as text; a tail with no `status` equals "Active"; `savedAt` and `version`). Print
  each allowed difference that was used, and how often, so nothing hides behind them.
- **The frozen sample too:** the same comparison on `tests/fixtures/sample_2026-10-08.json.gz`, loaded into an empty
  copy (§9 says how money per flight is loaded for it).
- **Load twice:** running the loader a second time changes no rows.
- **The flight rules:** for every rotation, the legs' UTC weekdays, departure minutes and block times turn back into
  the old frequency's local days and times exactly (§4's worked example, DEL–JFK `z5qbaeg`, as a named test), and
  every return's day follows the old planner's rule.
- **Matching:** after the refresh, the share of `game_flights` rows with both money and loads, and the rows left
  one-sided with the reason; `game_loads`, `game_flight_pnl` and `game_ops_recent` still return exactly what they did
  before the migration (the before-and-after check from pull request 3).
- **Unchanged outside:** `export_capture()`, `export_for_report('planner')`, `site_public()` and `planner_loads` as
  before; the real-saves step passes.
- **Speed:** how long `planner_state_get()` and `planner_loads_get()` take on the copy.

## Rules for the helper
- Follow `CLAUDE.md`. Read `.claude/skills/supabase-postgres-best-practices/SKILL.md` and its rule files before writing
  SQL. Read the previous builds' migrations (`20261009210000_planner_tables.sql`, `20261009230000_capture_data.sql`)
  and their tests for the conventions already set (actor, change log, `private`, grants, the before-and-after check).
- The planner (`web/planner/index.html`, about 580 KB) is the source of truth for the old JSON's meaning: grep for the
  parts you need (`computeFreq`, the return-day rule, `ref.consts`, `CODE_AL`, `applyCaptureCash`, `loadLoads`),
  never read it whole, and don't change it.
- **Never connect to the live database or use the Supabase connector tools.** Last night's backup is only reachable
  inside GitHub Actions: test by pushing and reading the *Database rehearsal* result. Docker is available here for
  trying SQL on an empty local Supabase.
- Work on branch `data-load`, open the pull request with the REST API (`gh api repos/GiteshJain/Equinox/pulls …`;
  GraphQL is blocked), and don't merge.
- `bash tests/run_all.sh` and the *Database rehearsal* must pass before asking for a merge.

## Done when
- The rehearsal passes with every proof above `ok`, and a deliberate failure was seen to fail, then removed (for
  example, one leg's departure minute off by one).
- The pull request says what changed, how long the migration and the getters take, which allowed differences were used
  and how often, any `extra` keys, the matching share, and anything in the design that turned out wrong or unclear.
- After "merge", the migration goes to live when no capture is running, and the Building chat checks the getters
  against live `planner_state` and `planner_loads`.
