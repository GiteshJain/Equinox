# Build spec: the new planner's Home screen (#18 build, pull request 5) — 13 Oct 2026

**Why:** step 5 of the build order (`docs/design/2026-10-12-planner-app.md` §13), the first real screen. Home uses the
most shared parts (the map, the attention checks, the to-do board, the airline colours), so it sets the pattern every
later screen copies. It also gives the planner its lighter start (design §5, the 12 Oct note). The game is paused and
the old planner frozen (manual §1): **nothing in `web/planner/` changes.**

**Outcome when done:** `/planner/next/` opens on a Home that shows what the old Home shows, from the same data, with
the same figures, on a phone too:
- **key figures:** aircraft, routes flying, flights a day, seats a day, average economy load over 7 days;
- **the network right now:** the globe with every route and where each aircraft is, at the current UTC time, with the
  day and night line, as the old Home draws it;
- **aircraft on order:** each aircraft not yet flying, its airline, type, base and when it arrives;
- **needs attention,** grouped as the old Home groups it (capture, backup, nightly jobs, to-dos, one-week checks due,
  maintenance, turns and positions, night bans, flight numbers used twice, airport departure caps, routes to fix, can
  order, monthly checks, interline), each item linking to where it's fixed, with **×** to dismiss and **show again**;
- **coming up:** the next 14 days (one-week checks and to-dos);
- **the to-do board:** open items with their steps, tick when done, add one, delete one, and the done ones of the last 7
  days folded away.

## What to build
The design is the specification: §2, §4 to §7, §9 (Home's row), §10, §14. The old Home is the reference for what's
shown and how it's worked out: `renderHome`, `todoBoard`, `ATT_KIND` and `attGrouped`, and the globe code (search
`THREE` and `terminator`) in `web/planner/index.html`. Where the design and this spec disagree, stop and say so.

### 1. The lighter start (design §5)
- `rules_input()` gains `p_routes text default 'all'`. With `'flown'` it gives only routes that have rotations, and only
  the airports those routes, the legs, the bases and the aircraft use. Everything else in the document is unchanged.
  `export_for_report('rules')` keeps the full document.
- The planner starts with `rules_input(world, 'flown')`. Say in the pull request how big it is on the copy (aim: under
  200 KB, from about 1 MB).
- A test in `rules_input_test.sql`: `'flown'` holds every route with a rotation and no other; every airport a flown
  route, leg, base or aircraft uses is there; `'all'` is unchanged.

### 2. The screen (`app/planner/src/screens/home/`)
- **Figures from their one home (#19):** key figures, attention checks for maintenance, turns, positions, night bans,
  flight numbers and airport caps, and the map's positions come from the library (`lib/rules/`) on the rules input. The
  capture, backup and jobs warnings come from `capture_status()`, `job_runs` and `backup_runs`. The average load
  comes from `airline_cards()`. "Can order" comes from `airline_cards()`'s `can_order_now`. Routes to fix come from
  `growth_signals()`. Nothing on Home works out a figure itself.
- **To-dos:** read from `todos` and `todo_items`; tick, add and delete through `planner_save()` (one action each,
  all or nothing, with the clash message from the shell). Deleting asks once ("Delete this to-do?") in the page, never
  a browser dialog.
- **Dismissals:** read from `dismissals`; × adds one and **show again** removes them, through `planner_save()`, with
  the same keys the old planner uses, so an item dismissed in either planner stays dismissed in both.
- **Aircraft on order:** the old Home's **File into planner** button opens the same flow in the old planner for now
  (a link to `/planner/`). Filing moves into the new planner with Tails (pull request 7), where the aircraft live. With
  the game paused, nothing is filed meanwhile.
- **The globe:** three.js, pinned, loaded only on Home, with the world outline from `web/assets/world.js` (read the
  file the website uses rather than copying it). It redraws aircraft positions once a minute. With reduced motion asked
  for, it doesn't spin.
- **Phones:** at 380 px, the boards stack in one column, the globe fits the width, and nothing scrolls sideways.
- **Shared parts** go in `src/ui/` for later screens: the board (a titled panel), pills, the attention list, the airline
  mark (logo or colour dot), dates as the old planner writes them ("today", "overdue · 9 Oct").
- **Every figure on screen** carries `data-figure="<name>"` with the same names as the saved answers
  (`tests/fixtures/planner_numbers.expected.json`: "home: key figures", "home: aircraft on order", "home: needs
  attention"), so the side by side can read them.

### 3. Checks
- **Unit tests (Vitest):** the attention grouping and order, dates as words, the dismiss keys, the to-do sort (open
  first by date, done in the last 7 days folded).
- **In the rehearsal, a new test `tests/home_side_by_side_test.py`,** on last night's copy at a frozen moment, signed in
  as the test staff user in both planners:
  1. key figures, aircraft on order, needs attention (every item's group, text and link), coming up and the to-do list
     must equal the old Home's. Any difference fails and names the board, the item and both values;
  2. real saves in the new planner: tick a to-do, add one with two steps, delete it, dismiss an attention item and show
     it again. Each writes exactly its rows, logged as planner with the tab's ID; the old planner then shows the same
     to-dos and dismissals;
  3. a preview address shows Home and sends no write;
  4. at 380 px: no sideways scroll, no errors; a screenshot at 380 px and at 1280 px kept as the run's `home-screens`
     artifact for review.
- `tests/planner_next_test.py`: Home is no longer a placeholder; the other eight still are.
- The time limit stays 30 minutes; say how long the run took.
