## How to work
1. **Small things yourself** (under about five minutes, no long reading): a to-do, a rule sentence with its rule
   history and project copies, a quick figure from the database, reading a worker's report, a merge.
2. **Everything else to a worker.** Start an agent in the background with the brief below, its model set by the kind
   of job: **Fable for a scheduling job** (a new aircraft's schedule, a plan card, a retime; Gitesh, 11 Nov: "new
   schedules should come from fable too"), **Opus for a build or a review job**. One job each. Say first what is
   running and roughly how long. The setting works: a test worker on 11 Nov, set to Opus, answered "Opus 5.5
   (claude-opus-5-5)". Fable as a worker's model is not tested yet, so have the first scheduling worker say in its
   report which model it ran on, and tell Gitesh. A worker's start alone used 69,457 tokens in the test, so give a
   worker only a job worth that, and never start one for a question you can answer from the database in a query or
   two.
3. **Stay light.** Do not read the map, the planner guide, the table guide, code or long query results yourself. If a
   question needs them, that is a worker's job. The Audit chat did its own reading and filled once in two days.
4. **Keep a worker for a sitting.** For follow-ups on the same job, continue the same agent; do not start a new one.
5. **A worker never decides.** When it sends back a choice, put it to Gitesh as a brief (manual §1), one at a time.
6. **Check before you tell him.** Take the two or three figures a decision hangs on and check them against the
   database.
7. **Builds:** one at a time. The worker clones its own copy, opens a pull request and stops. Wait for the checks with
   one background wait, read the pull request against its spec, never ask for "merge" while a check is red. On
   "merge", merge it, apply any database change to live as manual §1 says, and check it.
8. **Every job ends in something that lasts:** a pull request, a plan card, a file, a to-do. Workers live inside your
   session and are lost if it ends.
9. **A worker's lesson goes into its kind's note** (`claude/handover-building.md`, `-scheduling.md`, `-review.md`).
   Workers read those for tools and lessons, because they have no memory.

## The brief you give a worker
```
Job: one sentence.
Why: what Gitesh wants, in his words where possible.
Read first: the files this job needs, and no others.
Facts: what you already know (figures with their source, ids, to-do numbers).
Do: the steps, or the result wanted.
Do not: decide anything that is Gitesh's; touch anything outside this job; push to main or merge;
        change the live database's structure; publish to the website unless this brief says so.
Stop and report when: you reach a choice; something outside the job looks wrong; the job is growing well past its size.
Report: what you did, what you found (figures with sources), what you could not do, what needs deciding,
        and any lesson the next worker of your kind should know. Short.
```

## Learned on the first day
- **Attach the repository first:** `add_repo` for GiteshJain/Equinox with push access, then one clone to
  `/home/claude/equinox`. Workers make their own copy from that folder and set `origin` to GitHub when they need to push.
- **GitHub is REST only here** (`gh api repos/GiteshJain/Equinox/...`); `gh pr list` and `gh run view` are refused.
- **Continue a worker with SendMessage** (load it with ToolSearch). Its report arrives by itself; never poll.
- **A worker's file isn't kept until it is pushed.** Commit a brief to main yourself (look for a run in progress first)
  and push a spec's branch as soon as the worker reports.
- **Syncing a project copy costs a full read once per chat, then nothing.** `project_write` with `local_path` refuses
  until this chat has read that project file whole (the manual about 22,000 tokens, the rule history about 33,000),
  and after the chat's first write of it, later syncs go straight through. Workers can't write project files. So: put
  a rule's new sentence and its history entry in the build's pull request, and sync the two copies yourself after the
  merge. The map's copy (`claude/architecture.md`) has not been read by this chat and is behind main (to-do 234). A
  decision that isn't in force until it is built is recorded in the brief's Outcome and on the to-do, not in the
  manual.
- **Three wrong estimates on the first day, all from quoting before measuring:** "about an hour" for a 10-minute
  build, "45 minutes" for a 20 to 31 minute rehearsal, and "a worker will sync the copies".
- **Wait for checks with one `send_later`,** set for when the run should end; a background shell command is stopped a
  few minutes after the reply. A worker's report arrives by itself.
- **A changed to-do is a new to-do:** close the old one pointing to it. Don't retitle (done once to 233, put back).
- **The capture day starts at 10:00 UTC,** so the 09:30 UTC run belongs to the day before and the daily world scan comes
  with the 21:30 run.
- **The rehearsal takes 20 to 31 minutes,** not 45 (that was one hung run). Measure before quoting a time to Gitesh.
- **Give the day's time from the database** (`now() at time zone 'Asia/Kolkata'`) in a to-do's note, not from memory.
- **Workers so far:** build workers on Opus 5.5 only, each about 70,000 tokens to start and 150,000 to 420,000 by the
  end of a job. A fresh worker for each new job is cheaper than continuing one past about 300,000. No scheduling worker

## Lessons from the Audit chat
- **Check the fact and the date before calling something late or broken.** It said the bank statement kept three days
  (24 hours), that the 1,500-line stop might be the game's (it was the script's), and that the retime pass was piling
  up (it was on its date).
- **Ask how he uses a thing before designing for it.** It designed for a phone; he uses the planner on a computer.
- **A push to `main` cancels the check still running on the commit before it.** The check then runs on the new
  commit, which contains the old one. Look for a run in progress before pushing.
- **Measure what he actually feels.** The planner's slowness showed in the request log (16 failed requests in one
  morning), not in timing one call alone.
